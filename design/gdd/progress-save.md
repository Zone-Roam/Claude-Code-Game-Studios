# 进度、三星与存档

> **Status**: In Review（2026-10-30 按 /design-review 修订，待复审）
> **Author**: 用户 + 主会话（lean 模式）
> **Last Updated**: 2026-10-30
> **Last Verified**: 2026-10-30
> **Implements Pillar**: 5 攒得踏实（星级只看玩家自己打得怎样）、3 故事决定这一回打什么仗（解锁顺序跟着回目走）

## Summary

赢一回至少一星，三星看“守得多稳”：敌将模式看丢了几颗心，压境模式看最下一排被压了多久，粮草模式看连不上的次数和余粮。MVP 三回一开始全开，竖切片起赢了才解锁下一回；武将也是赢了哪回得哪位，由进度推出来，不单独存。每一回还记住上次带的阵容。进度存在本机，数据带版本号；存不了的时候游戏照样能玩，只是关掉后从头来，并提示一次。MVP 不做进度码（用户决定，放到竖切片）。

> **Quick reference** — Layer: `Feature` · Priority: `MVP` · Key deps: `对局流程与时钟、战场压力、回目编排与难度、选将与解锁`

## Overview

这个系统回答两个问题：这一回打得怎样（星级），以及下次打开时从哪儿接着讲（存档）。星级是“再来一回”的第二个理由（概念文档：回头冲三星），而且它只能来自玩家自己的操作，不能和运气、付费挂钩（支柱 5、反支柱：不赌、无抽奖）。门禁留下的待定项“三种模式各自的三星标准”在这里定，用户已选“守得多稳”（2026-10-27）：三种模式各量一种“险”，险越少星越多。存档面对的最大未知是小红书 WebView 的存储行为（是否会被清、是否可用），所以设计成“存不了也不坏”：所有读写都可能失败，失败时降级而不是报错。

## Player Fantasy

“这一回守得稳。”结算卡上三颗星章一颗颗盖下来；没拿满时，卡上写着差在哪（“丢了 1 颗心”），玩家知道下次该怎么守。输了也不丢已经攒下的星。

## Detailed Design

### Core Rules

**星级**

1. 只有赢才评星，最少 1 星，最多 3 星。输了 0 星，不覆盖已有记录。
2. 三种模式各量一种“险”（指标由战场压力在 `metrics()` 里给出，经结果对象传来）：

   | 模式 | 指标 | 3 星 | 2 星 | 1 星 |
   |---|---|---|---|---|
   | 敌将反击 | `heartsLost` 结算时少了几颗心（净值：刘备补回的心算回来，用户决定 11，2026-10-30） | ≤ `t3`（缺省 0） | ≤ `t2`（缺省 1） | 其余 |
   | 敌军压境 | `dangerMs` 最下一排有块的累计游戏时长（整回，含空行下压阶段） | ≤ `t3`（缺省 2000 ms） | ≤ `t2`（缺省 8000 ms） | 其余 |
   | 粮草有限 | `misses` 连不上的次数、`foodLeft` 余粮 | `misses == 0` 且 `foodLeft ≥ foodT3`（缺省 2） | `misses ≤ missT2`（缺省 2） | 其余 |

   敌将的阈值只看丢了几颗心，和总心数无关，所以回目把心数改成 2 或 4 也照样成立。
3. **阈值覆盖**：回目数据的 `stars` 字段可以覆盖缺省值，形状按模式：
   - 敌将、压境：`{t3, t2}`，非负整数，且 `t3 ≤ t2`；
   - 粮草：`{foodT3, missT2}`，非负整数。
   - 形状不对或 `t3 > t2`：开发版报错；正式版忽略覆盖、用缺省值（“回目编排与难度”的加载器执行这条检查）。
4. 用时和连斩**不直接参与**评星（它们和“守得稳”无关；概念文档支柱 5 已同步改写）。结算卡上显示本回的用时和最高连斩，MVP 不保存最好记录。要说清楚的是：敌将的丢心数、压境的压线时长都会随手速变化（手快的人打断多、压线少），只有粮草的星级与快慢无关；“不惩罚手慢”只做到“不直接用用时评星”这一步，手慢的人要靠张飞和技能的时机补回来。
5. **结算**：对局流程进入“结束”时调用 `settle(result)`（`result` 的字段见“对局流程与时钟”规则 8），本系统当即算星、更新记录、写存档，返回：

   ```
   SettleOutcome {
     stars: 0 | 1 | 2 | 3       // 本回
     bestStars: 0 | 1 | 2 | 3   // 更新后的历史最好
     isNewBest: boolean         // 本回星数高于更新前的最好
     reasonLine: string | null  // 赢了但没满 3 星时的一句原因；满星或输了为 null
     saved: boolean             // 这一回的结果是否已写进本机存储：本次写入成功为 true；写入抛异常、或本来就处于“只读”“仅内存”状态为 false
   }
   ```
6. **原因一句**（`reasonLine`，用读的字）：
   - 敌将：“丢了 {heartsLost} 颗心”。
   - 压境：“压线 {秒} 秒”，秒 = `ceil(dangerMs / 100) / 10`，保留一位小数（向上取整，这样 2001 ms 显示“2.1 秒”，玩家看得出为什么丢了 3 星）。
   - 粮草：`misses > 0` 时“连不上 {misses} 次”；否则“余粮只剩 {foodLeft} 份”。
7. 每一回保存**最好成绩**：星级取历次最高；同时记录赢的次数和打的次数。

**解锁**

8. **MVP：三回一开始全部解锁**（用户决定，2026-10-27：第一回吕布是硬仗，手慢的人如果被卡在第一回，就测不到压境和粮草，MVP 验证不了核心假设）。书目里仍按回目顺序排列，星级照常记录。
   **竖切片起**恢复按故事顺序解锁：回目按“回目编排与难度”的顺序（只算能加载的回目）。第 n 回解锁的条件，满足任一即可：
   - 它是第一回；
   - 它前一回有胜场（`wins > 0`）；
   - 它后面任意一回有胜场（以后在中间插入新回目时，已经打过后面的人不会被重新锁住）。

   **“MVP 三回全开”只适用于没有选将系统的 MVP 包**（2026-10-30 核对）。选将与解锁从竖切片起才有，它和按故事顺序解锁一起上线，所以两条规则不会同时生效。即使有人在全开的包里先赢了后面的回目，也不会出错：武将解锁只看各回的 `wins`（规则 9 之后的“武将解锁”），主将和推荐阵容里的武将在那一回本来就可用（“选将与解锁”规则 8）。
9. 已解锁的回目可以随时重打。输一次不会让任何回目重新上锁。

   **武将解锁**（“选将与解锁”规则 5–8）：已解锁的武将 = 数据文件顶层的 `starters` + 所有 `wins ≥ 1` 且能加载的回目的 `unlock`。存档里**不单独存**，和回目解锁一样每次从进度推出来；本系统只提供各回 `wins`。所以：
   - 输一次不会让任何武将重新上锁（`wins` 只增不减）。
   - 因为“后面的回目有胜场”而解锁的回目，它自己的 `unlock` 要等玩家真的赢下它才得到。
   - 改版后某回的 `unlock` 换了人：按新数据推，已赢过那一回的玩家直接得到新武将，原来那位如果别处不给，就不再算已解锁。这是“不单独存”的代价，改 `unlock` 时要知道（见 Open Questions）。
   - 存储不可用时，武将解锁只在这一次页面会话里有效（规则 17）。

**存档**

10. 存档是一条记录，存在本机存储里，键名 `pslk.save`：

    ```
    {
      "v": 1,                         // 数据版本，正整数
      "chapters": {                   // 对象，不是数组
        "ch01": { "stars": 2, "wins": 3, "plays": 5, "loadout": ["guan_yu", "zhang_fei"] },
        "ch02": { "stars": 0, "wins": 0, "plays": 1 },   // 旧存档没有 loadout，也合法
        ...
      },
      "updatedAt": 1793000000000      // 毫秒时间戳，只用于排查
    }
    ```

    `loadout`（可选，2026-10-30 随选将系统新增）：这一回上次实际上阵的武将 id，按槽位顺序。它是可选字段，旧存档没有它也合法，所以 `v` **不升级**，仍是 1，也不需要迁移。它只用来在下次打开水牌时按上次的阵容填槽（“选将与解锁”规则 9、13），不参与评星和解锁。

    回目和武将的解锁状态都不单独存，由回目顺序、各回 `wins` 和回目数据推出来（规则 8、9）。顶层不认识的字段原样保留。
11. **校验**（读取时，先看版本再校验）：
    - 先读出 `v`：`v` 大于当前版本时按规则 15 处理，不按当前版本的结构判损坏（新版本的格式可能变了）。
    - 整条记录：必须能解析成对象，`v` 是正整数，`chapters` 是对象。不满足 → 视为损坏（规则 16）。
    - 每一条回目记录：`stars` 是 0–3 的整数，`wins`、`plays` 是非负整数，`wins ≤ plays`，且 `stars > 0` 时 `wins ≥ 1`。不满足的那一条**单独丢掉**，其余照用，开发版写日志。
    - 每一条回目记录里的 `loadout`（有才检查）：必须是数组，长度 1 到 `SLOT_MAX`（3），每一项是字符串，没有重复。不满足 → **只丢掉 `loadout` 这一项**，这一条回目记录的 `stars`、`wins`、`plays` 照用，开发版写日志。`loadout` 出错不算整条回目记录不合法。
    - 本系统只做上面的形状检查。“武将 id 认不认识”“长度是否超过这一回的 `slots`”“这位武将这一回能不能用”由“选将与解锁”在填槽时检查（它的 Edge Cases：同样只丢 `loadout`，按推荐阵容填）。
12. **写入时机**：`settle()` 时写一次。对局中途不写，切后台不写，点“回书目”放弃的一回不写。`loadout` 和星级同一次写：`settle()` 时把结果对象里本回实际上阵的武将列表写进这一回的记录，**赢输都写**（输了也记住阵容，下次打开水牌还是这一套）；放弃的一回不写。**`RoundResult.loadout` 为空数组时不写 `loadout` 这一项**：保留这一回原来存着的 `loadout`（原来没有就不写），绝不写入 `[]`（规则 11 判 `[]` 为非法）。存下来的 `loadout` 永远是 1–3 位武将。主将不能换，正常情况不会为空，这是兜底。
13. **先读后合并再写**：写入前重新读一次 `pslk.save`，逐回合并（`stars`、`wins`、`plays` 各取两边的较大值），再写回。这样两个页面同时开着、或存档在会话中途被别处改过时，不会互相抹掉。重读的结果按下面处理（先看版本，再做校验）：

    | 重读结果 | 处理 |
    |---|---|
    | 读本身抛异常 | 不写，转入“仅内存”（规则 17） |
    | 没有存档 | 直接用内存进度写入 |
    | `v` 大于当前版本（别的页面开着新版本） | 不写，转入“只读”，提示一次（规则 15） |
    | `v` 小于当前版本 | 先迁移再合并；迁移抛异常按“整条损坏”处理 |
    | 整条损坏（不是合法 JSON、结构不对） | 不清内存进度，直接用内存进度写入；不再覆盖 `pslk.save.bad` |
    | 某一条回目记录不合法 | 那一条以内存为准，其余照常合并 |

    `loadout` 不能取较大值，按下面合并：
    - 这次 `settle()` 的那一回：用本回实际上阵的阵容（最新的）；`RoundResult.loadout` 为空数组时按规则 12 保留重读到的（没有就用内存里的，再没有就不写这一项）。
    - 其他回目：重读到的记录里有合法的 `loadout` 就用它（它是最后一次写进存储的）；没有就用内存里的；两边都没有就不写这一项。

    合并完成后，合并后的记录同时成为新的内存进度；`bestStars` 和 `isNewBest` 按它算。
14. **启动时**：
    1. 先读 `pslk.save`（读本身抛异常 → 存储不可用，规则 17）。
    2. 再用独立的探测键 `pslk.probe` 做一次“写入—读回—删除”；探测失败而第 1 步读成功了（例如配额已满）→ 用读到的进度，但标记为“只能读”，按规则 17 处理写入。
    3. 之后以内存里的为准。
15. **版本迁移**：读到 `v` 小于当前版本时，按顺序逐版迁移（v1 → v2 → …），迁移成功后在下次 `settle()` 时写回新版本；迁移函数抛异常 → 视为损坏（规则 16）。读到 `v` **大于**当前版本（玩家装过更新的版本又回到旧版本）：按当前版本的规则尽力读出能读的回目记录作为内存进度，**不写回**，提示一次“存档来自新版本，这次的进度不会保存”。
16. **数据损坏**：把原始字符串另存到 `pslk.save.bad`（只保留一份，覆盖旧的；这一步失败就算了，不影响启动），然后从空白进度开始，提示一次“存档读不出来，已从头开始”。下一次 `settle()` 写入新存档。
17. **存储不可用**（隐私模式、WebView 禁用、读写抛异常、只能读）：进度只保存在内存里，不再尝试写；提示一次“这台手机存不了进度，关掉后要从头讲起”。运行中第一次写入失败时也转入这个状态，在下一次回到书目时提示“只能读、不能写”那一句（之前的进度仍在本机）。
18. **提示**：每种提示每次页面加载最多出现一次，显示在书目顶部的亮纸条上，点一下收起。同一时刻有几种待显示时，只显示优先级最高的一种：存不了 > 读不出来 > 来自新版本；其余的等它收起后、下一次回到书目时再显示。提示条只在书目出现，不进对局画面，不影响盘的布局。文案：
    - 完全存不了（读也失败）：“这台手机存不了进度，关掉后要从头讲起”。
    - 只能读、不能写：“这台手机存不了新进度，这次打的关掉后不会保留”。
    - 读不出来：“存档读不出来，已从头开始”。
    - 来自新版本：“存档来自新版本，这次的进度不会保存”。
19. 存档里出现回目数据里没有的 `id`（回目被删改过）：读取时忽略，合并写回时原样保留，不删除。
20. 不收集、不上传任何数据；不联网。

### States and Transitions

| 状态 | 进入 | 离开 | 行为 |
|---|---|---|---|
| 正常 | 启动读和探测都成功（含没有存档） | 写入失败 → 仅内存 | `settle()` 时合并写入 |
| 只读（新版本） | 读到 `v` 大于当前版本 | — | 不写；内存进度；提示一次 |
| 仅内存 | 读抛异常；探测失败；运行中写入失败 | — | 不再尝试写；内存进度；提示一次 |

### Interactions with Other Systems

| 系统 | 方向 | 数据 | 接口归属 |
|---|---|---|---|
| 对局流程与时钟 | 上游 | 进入“结束”时调用 `settle(RoundResult)`，拿回 `SettleOutcome`；`RoundResult` 要带本回实际上阵的武将列表 `loadout` | 结果对象由对局流程定义；`SettleOutcome` 由本系统定义 |
| 选将与解锁 | 双向 | 读：各回 `wins`（推出已解锁的武将）、各回 `loadout`（填槽）；写：经 `settle()` 记下各回 `loadout` | `loadout` 的存储形状和形状检查归本系统；内容检查和解锁公式归选将与解锁 |
| 战场压力 | 上游（经结果对象） | `metrics`：`heartsLost` / `dangerMs` / `foodLeft` 与 `misses` | 战场压力 |
| 回目编排与难度 | 上游（数据） | 能加载的回目顺序、`id`、`stars` 覆盖（加载器按规则 3 检查） | 形状和缺省值归本系统 |
| 界面与交互 | 下游 | `SettleOutcome`（结算卡盖章、原因一句）；书目的锁定和最好星级；提示条 | 本系统提供 |
| 图鉴（完整版） | 下游 | 已赢过的回目（解锁武将资料） | 本系统 |

## Formulas

The stars formula is defined as:

```
stars = 0                       如果 win == false
敌将、压境：
stars = 3  如果 risk ≤ t3
      = 2  如果 risk ≤ t2
      = 1  其余
粮草：
stars = 3  如果 misses == 0 且 foodLeft ≥ foodT3
      = 2  如果 misses ≤ missT2
      = 1  其余
```

其中敌将的 `risk = heartsLost`，压境的 `risk = dangerMs`。

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| heartsLost | int | 0 到 hearts − 1（赢时） | battle-pressure | 结算时少了几颗心（净值，`heartsMax − hearts`；见“战场压力”公式 hearts_net） |
| dangerMs | int | 0–∞ | battle-pressure | 最下一排有块的累计游戏时长，已向下取整 |
| misses | int | 0–∞ | battle-pressure | 连不上的次数 |
| foodLeft | int | 0–∞ | battle-pressure | 结束时的余粮（不小于 0） |
| t3、t2 | int | 0–∞，`t3 ≤ t2` | 缺省或回目覆盖 | 敌将缺省 0、1；压境缺省 2000、8000 |
| foodT3 | int | 0–6（安全范围，超出只警告） | 缺省或回目覆盖 | 缺省 2 |
| missT2 | int | 0–6（安全范围，超出只警告） | 缺省或回目覆盖 | 缺省 2 |

**Output Range:** 赢时 1–3，输时 0。阈值都含等号。
**Example:**
- 敌将模式丢了 1 颗心赢下 → 2 星。
- 压境模式最下一排有块共 5200 ms → 2 星，原因“压线 5.2 秒”。
- 粮草模式连不上 0 次、余粮 1 → 不满足 3 星（余粮 < 2）→ misses ≤ 2 → 2 星，原因“余粮只剩 1 份”。

The best_record formula is defined as:

`best.stars = max(best.stars, stars)`；`wins += win ? 1 : 0`；`plays += 1`；合并写入时三项各取两边较大值

**Output Range:** 星级只升不降。
**Example:** 历史 2 星，这次 1 星赢下 → 仍是 2 星，`wins + 1`，`isNewBest = false`。

**关于阈值的说明**：缺省阈值没有经过试玩，只按“开发者本人打一遍大概能拿 2 星”估。粮草的 `foodT3 = 2` 恰好等于第七回的 `slack`（2），所以第七回的 3 星等于“一份粮都不浪费、一次都不连错”，或者用好张飞（+3 粮），这是有意的高标准；第四回 `slack` 3，零失误时余粮 3，也满足 ≥ 2，3 星相对宽一点。粮草回是第四回和第七回（第三回已改为敌将）。阈值以后调整时，已经存下的星不重算（原始指标没有存）。

## Edge Cases

- **如果一回在分出胜负之前被关掉**（杀进程、刷新）或点“回书目”放弃：这一回不计，不写入，`plays` 也不加。
- **如果盖章演出途中关掉页面**：写入成功时，星级在进入“结束”时已经写入，不丢。写入失败时（转入“仅内存”），关掉就丢了这一回；为此结算卡上会加一行“这一回没存上”（见“界面与交互”），不只靠书目的提示条。
- **如果同一回被 `settle()` 两次**：重复调用由对局流程保证不会发生（开发版断言）。本系统用 `RoundResult` 里的 `chapterId + attempt`（“对局流程与时钟”规则 12，`attempt` 同一页面会话内每次开局加 1，“再来一回”也加 1）记下最近一次已结算的键；同键再来就直接返回上次的 `SettleOutcome`，不写档、不重复加 `plays`。键只放内存，不存档。
- **如果写入抛异常**：转入“仅内存”，不重试，不打断结算卡。
- **如果读到 `v` 更新的存档**：只读，尽力读出可用的记录，提示一次（规则 15）。
- **如果存档损坏**：备份到 `pslk.save.bad`，从头开始，提示一次（规则 16）。
- **如果某一条回目记录不合法**（例如 `stars: 7`、`wins > plays`）：只丢这一条，其余照用。
- **如果玩家清了小红书的缓存**：存档丢失，等同第一次打开。MVP 无法恢复（进度码放到竖切片）。程序区分不了“被清了”和“第一次打开”。
- **如果两个页面同时开着同一个游戏**：每次写入前先读后合并（规则 13），两边的进度都保留。
- **如果回目阈值写错**：见规则 3。
- **如果赢下最后一回**：没有下一回可解锁，照常记星。
- **如果压境的 `dangerMs` 恰好等于 2000**：3 星（阈值含等号）；8000 → 2 星；8001 → 1 星。
- **如果读到的旧存档没有 `loadout`**：合法，`v` 仍是 1；水牌按推荐阵容填槽。下一次 `settle()` 时补上这一回的 `loadout`。
- **如果某一回的 `loadout` 形状不对**（不是数组、空数组、超过 3 项、有非字符串、有重复）：只丢这一项，这一回的星级和胜场照用；下一次合并写回时这一项不再写出（除非这一回又结算了一次）。
- **如果 `loadout` 形状合法但内容不对**（不认识的武将 id、超过这一回的 `slots`、改版后蓄力兵不在 `deck` 里）：本系统不管，原样保留；由“选将与解锁”填槽时跳过或丢掉，下一次这一回结算时被新阵容覆盖。
- **如果两个页面先后结算了同一回、阵容不同**：后写的那一次赢（它的 `settle()` 用的是本回阵容）。星级、胜场照常取较大值。
- **如果启动时已处于“只读”“仅内存”**：`loadout` 和星级一样只记在内存里，这次会话里“再来一回”仍能沿用；重新加载后丢失。
- **如果玩家只靠“后面回目有胜场”解锁了前面的回目**：那一回能打，但它的 `unlock` 武将要等赢下它才得到（规则 9）。

## Dependencies

- **依赖（上游）**：对局流程与时钟（硬：结果对象和 `settle()` 时机，结果对象里的 `loadout`）、战场压力（硬：评星指标）、回目编排与难度（硬：回目顺序、`id`、阈值覆盖的检查）。
- **双向**：选将与解锁（design/gdd/general-loadout.md；硬）。它读本系统的各回 `wins` 推出已解锁的武将，读各回 `loadout` 填槽；本系统存它交来的 `loadout`（经结果对象）。
- **被依赖（下游）**：界面与交互（硬：结算卡、书目、提示条）、图鉴（完整版，软）。
- 存储方式不变（ADR-0004）：只加一个可选字段，不升 `v`。
- 清除效果的 `maxCombo`、武将技能的 `skillsUsed` 经结果对象传来，本系统只转交给结算卡显示，不评星、不保存。

## Visual/Audio Requirements

依据美术圣经第 3、4、7 节：

- 三星是圆角五角星章：得到的是描金加墨边，没得到的是淡墨虚线。描金只用在“技能可用”和三星这两处。
- 胜利卡盖章：卡进场 220 ms；停 200 ms 后印以 1.15 倍落到 1.0（140 ms），压实 120 ms，不回弹；三星逐颗盖，间隔 160 ms。
- 书目里，已赢过的回目显示最好星级；未解锁的显示成虚线框，写“未开讲”。
- 提示条用读的字（黑体 18 px），亮纸底，不用警告色，不挡操作。

## Game Feel

- 星级要让玩家一看就知道“哪里还能更稳”：没拿满星时结算卡上写原因一句（规则 6）。
- 输不丢东西：已有的星和解锁永远不会因为一次输而减少。

## UI Requirements

胜利卡（星章、原因一句、下回预告、按钮）、失败卡、书目（锁定、星级）、提示条。见“界面与交互”。

## Acceptance Criteria

- **GIVEN** 敌将模式赢、`heartsLost = 0`，**WHEN** `settle()`，**THEN** `stars = 3`，`reasonLine = null`。
- **GIVEN** 敌将模式赢、`heartsLost = 1`，**WHEN** `settle()`，**THEN** `stars = 2`，`reasonLine = '丢了 1 颗心'`。
- **GIVEN** 敌将模式赢、`heartsLost = 2`，**WHEN** `settle()`，**THEN** `stars = 1`。
- **GIVEN** 敌将模式、回目 hearts = 4、赢时 `heartsLost = 3`，**WHEN** `settle()`，**THEN** `stars = 1`，没有断言报错。
- **GIVEN** 敌将模式、3 颗心、挨打 2 次后刘备补回 1 颗、之后没再挨打，赢（结果对象里 `heartsLost = 1`），**WHEN** `settle()`，**THEN** `stars = 2`，`reasonLine = '丢了 1 颗心'`（按净值，不按挨打次数）。
- **GIVEN** 压境赢、`dangerMs = 2000`，**WHEN** `settle()`，**THEN** 3 星；2001 → 2 星；8000 → 2 星；8001 → 1 星。
- **GIVEN** 压境赢、`dangerMs = 5201`，**WHEN** `settle()`，**THEN** `reasonLine = '压线 5.3 秒'`；`dangerMs = 2001` → “压线 2.1 秒”。
- **GIVEN** `pslk.save` 内容是 `"abc{"`，**WHEN** 启动后赢下 ch01，**THEN** `pslk.save` 变成合法的 v1 记录，里面有 ch01 的胜场；`pslk.save.bad` 里仍是 `"abc{"`。
- **GIVEN** 存档里 ch01 是 `{stars: 7, wins: 1, plays: 1}`，**WHEN** 启动后赢下 ch02，**THEN** 写回的 `chapters` 里没有 `ch01` 这个键，`ch02` 的 `wins = 1`，其余字段不变（启动时 ch01 已按规则 11 丢掉，规则 13 末行“那一条以内存为准”）。
- **GIVEN** 启动后，另一个页面把 `pslk.save` 改成 `v = 2`，**WHEN** 本页赢下一回，**THEN** 不写入，转入只读，提示“存档来自新版本，这次的进度不会保存”。
- **GIVEN** 有存档、读取成功但探测失败（只能读），**WHEN** 进入书目，**THEN** 已有进度照常显示，提示“这台手机存不了新进度，这次打的关掉后不会保留”。
- **GIVEN** 粮草赢、`misses = 0`、`foodLeft = 2`，**WHEN** `settle()`，**THEN** 3 星。
- **GIVEN** 粮草赢、`misses = 0`、`foodLeft = 1`，**WHEN** `settle()`，**THEN** 2 星，`reasonLine = '余粮只剩 1 份'`。
- **GIVEN** 粮草赢、`misses = 2`、`foodLeft = 5`，**WHEN** `settle()`，**THEN** 2 星，`reasonLine = '连不上 2 次'`；`misses = 3` → 1 星。
- **GIVEN** 任意模式输，**WHEN** `settle()`，**THEN** `stars = 0`，已有最好星级不变，`plays + 1`，`wins` 不变。
- **GIVEN** ch01 历史 2 星，**WHEN** 以 1 星赢下，**THEN** `bestStars = 2`，`isNewBest = false`，`wins + 1`。
- **GIVEN** MVP 包（没有选将系统）、新存档，**WHEN** 启动，**THEN** ch01、ch02、ch03 都可以点。
- **GIVEN** 竖切片的解锁规则、新存档，**WHEN** 启动，**THEN** 只有第一回解锁；赢下第一回后第二回解锁；在第二回输一次后第二回仍解锁。
- **GIVEN** 竖切片的解锁规则、存档里第三回有胜场、第二回没有，**WHEN** 启动，**THEN** 第一到第三回都解锁。
- **GIVEN** 没有存档、读取抛异常（存储完全不可用），**WHEN** 进入书目，**THEN** 提示条显示“这台手机存不了进度，关掉后要从头讲起”；**WHEN** 同一次页面会话里赢下 ch01（2 星），**THEN** 书目上 ch01 显示 2 星，`SettleOutcome.saved = false`；**WHEN** 重新加载页面，**THEN** ch01 没有星级记录（MVP 三回仍然都能点）。
- **GIVEN** 存储正常，**WHEN** 运行中第一次写入抛异常，**THEN** 结算卡照常显示且 `saved = false`；回到书目时提示条文案为“这台手机存不了新进度，这次打的关掉后不会保留”；**WHEN** 之后再结算 2 回，**THEN** 注入的存储端口 `setItem` 调用次数为 0（与第一次失败后的调用计数相比不增加）。
- **GIVEN** 存储正常，**WHEN** 启动，**THEN** `pslk.save` 的内容没有被探测改动，`pslk.probe` 不存在。
- **GIVEN** `pslk.save` 内容是 `"abc{"`，**WHEN** 启动，**THEN** 原字符串存进 `pslk.save.bad`，进度从空白开始，提示条显示“存档读不出来，已从头开始”。
- **GIVEN** `pslk.save` 里 `chapters` 是数组，**WHEN** 启动，**THEN** 视为损坏，处理同上。
- **GIVEN** 存档里 ch01 `{stars: 7, wins: 1, plays: 1}`、ch02 合法，**WHEN** 启动，**THEN** 丢掉 ch01 这一条，ch02 照用。
- **GIVEN** 存档 `v = 2`、当前版本 1、其中 ch01 为 `{stars: 2, wins: 1, plays: 1}`，**WHEN** 启动，**THEN** 书目上 ch01 显示 2 星（从新版本存档里尽力读出），提示“存档来自新版本，这次的进度不会保存”；**WHEN** 再赢下 ch02，**THEN** `pslk.save` 的内容不变。
- **GIVEN** 存档里有 `ch99`（回目数据里没有），**WHEN** 打完 ch01 写回，**THEN** `ch99` 的记录原样保留。
- **GIVEN** 页面 A 赢下 ch01 并写入后，页面 B（内存里没有 ch01 的胜场）赢下 ch02，**WHEN** B 写入，**THEN** 存档里 ch01 和 ch02 的胜场都在。
- **GIVEN** 存储正常、一回已经进入“结束”、盖章演出途中关掉页面，**WHEN** 重新打开，**THEN** 这一回的星级和 `plays` 已经记上。
- **GIVEN** 这一回的写入抛异常，或启动时已处于“只读”“仅内存”状态，**WHEN** 结算卡（胜利卡或失败卡）出现，**THEN** `saved = false`，卡上有“这一回没存上”一行；写入成功时没有这一行。
- **GIVEN** 一回在分出胜负之前刷新页面，**WHEN** 重新打开，**THEN** 这一回的 `plays` 没有增加。
- **GIVEN** 回目 `stars` 覆盖为 `{t3: 1, t2: 2}`（敌将），**WHEN** 赢时 `heartsLost = 1`，**THEN** 3 星。

**阵容与武将解锁**

- **GIVEN** 存档 `v = 1`、ch01 是 `{stars: 2, wins: 1, plays: 2}`（没有 `loadout`），**WHEN** 启动，**THEN** 这一条合法，ch01 显示 2 星，没有提示条，存档没有被改写。
- **GIVEN** 上一题的存档，**WHEN** 以关羽、张飞出阵输掉 ch01，**THEN** 写回的 ch01 是 `{stars: 2, wins: 1, plays: 3, loadout: ["guan_yu", "zhang_fei"]}`，`v` 仍是 1。
- **GIVEN** 存档里 ch02 是 `{stars: 1, wins: 1, plays: 1, loadout: "zhao_yun"}`（不是数组），**WHEN** 启动，**THEN** ch02 的 1 星和胜场照用，`loadout` 被丢掉；开发版日志里有 ch02 和 `loadout`。
- **GIVEN** 存档里 ch02 的 `loadout` 是 `["zhao_yun", "zhao_yun"]` 或 `[]` 或有 4 项，**WHEN** 启动，**THEN** 处理同上。
- **GIVEN** ch02 已存 `loadout = ["zhang_fei", "guan_yu"]`，**WHEN** 结算 ch02 时 `RoundResult.loadout = []`，**THEN** 写回的 ch02 里没有 `[]`，`loadout` 仍是 `["zhang_fei", "guan_yu"]`；**GIVEN** ch02 原来没有 `loadout`，**THEN** 写回后仍没有 `loadout` 这一项。
- **GIVEN** 同一页面会话里 `chapterId = ch01, attempt = 1` 已结算，**WHEN** 又收到同样的 `settle()`，**THEN** 返回与上次相同的 `SettleOutcome`，`plays` 不再加，没有新的写入；**WHEN** 收到 `attempt = 2`（再来一回），**THEN** 正常结算。
- **GIVEN** 存档里 ch02 的 `loadout` 是 `["zhao_yun", "lv_bu"]`（形状合法），**WHEN** 启动，**THEN** 本系统原样保留这一项，ch02 的星级照用（内容检查归“选将与解锁”）。
- **GIVEN** 一回在分出胜负之前点“回书目”放弃，**WHEN** 查看存档，**THEN** 这一回的 `loadout` 没有变。
- **GIVEN** 页面 A 写入了 ch01 的 `loadout = ["guan_yu"]`，之后页面 B（内存里 ch01 的 `loadout` 是 `["zhang_fei"]`）结算 ch02，**WHEN** B 写入，**THEN** 存档里 ch01 的 `loadout` 仍是 `["guan_yu"]`，ch02 是 B 本回的阵容。
- **GIVEN** `starters = [guan_yu, zhang_fei]`、ch01 的 `unlock = zhao_yun`、新存档，**WHEN** 赢下 ch01，**THEN** 存档里只多了 ch01 的记录，没有任何“已解锁武将”字段；重新加载后，已解锁的武将是关羽、张飞、赵云。
- **GIVEN** 存档里 ch03 有胜场、ch02 没有，ch02 的 `unlock = zhuge_liang`，**WHEN** 启动，**THEN** ch02 可以点，但诸葛亮不在已解锁的武将里。

## Open Questions

- 小红书 WebView 的本机存储会不会被清、多久清一次？（负责：平台核实；目标：竖切片前。门禁 Accepted Risk。）
- 进度码（复制一串字符恢复进度）放在竖切片做，格式和防篡改程度到时再定。（用户决定，2026-10-26。）
- 压境的 `dangerMs` 阈值是绝对毫秒；`interval` 改得很大时一次险情就可能越过 2 星线。要不要改成按 `interval` 换算？（负责：回目编排；目标：竖切片。）
- 第一回 3 星（一颗心都不丢）对中老年近乎不可达，这是“吕布硬仗”的一部分还是要调？（负责：试玩。）
- 小红书小工具每次发版后，页面的来源（origin）会不会变？变了本机存储就换了一份，等于清档。（负责：平台核实；目标：竖切片前。）
- 武将解锁不单独存，改版时改了某回的 `unlock`，老玩家手里的武将会跟着变（可能“失去”一位）。要不要在存档里另记一份“已得武将”作为只增不减的兜底？那会是 `v` 升到 2 的改动。（负责：用户；目标：正式版 10 回的编排定稿前。）
